# 在线更新与正式分发

设置页的「应用更新」由用户主动触发，查询 GitHub Releases 的 latest 接口。默认仓库为 `Lance0174/KinaraMusic`。不启动定时后台检查、不上传账号信息或播放记录。

## 用户流程

1. 检查更新：只接受正式版本；没有 Release、当前版本相同或更高时显示没有可用更新。
2. 阅读说明并下载：显示下载进度，允许取消；失败可重试。
3. 验证：实际字节数、GitHub 提供的 SHA-256、包名、版本名和递增的 versionCode 均须匹配，签名须与当前已安装应用一致。
4. 安装：首次使用时打开 Android 的「允许安装未知应用」设置，用户允许后返回并再次点击安装。系统安装界面仍需用户确认。

下载暂存在应用私有缓存。FileProvider 仅能分享 `cache/updates/`，不会暴露其它缓存、设置或凭据。安装前重新读取摘要并核验包身份。网络客户端在每次连接前只允许当前仓库的 GitHub release 路径与 GitHub 资产 CDN，禁止明文、异常端口与携带身份信息的地址，不附加账号 Cookie 或 Authorization。

## 发布约定

- 稳定标签格式为 `v主版本.次版本.补丁版本`，例如 `v1.4.0`；APK 的 versionName 对应 `1.4.0`，versionCode 必须递增。
- 对应的 ARM64 安装包必须命名为 `Kinara-1.4.0-arm64-v8a.apk`（版本号随标签变化）。资产上传完成，GitHub API 的 `digest` 字段须为 `sha256:...`。
- 使用外部保存的固定发布密钥签名，不能使用未签名 CI 产物或每次生成的新密钥。签名不一致将被拒绝；当前更新策略不支持换钥迁移。
- 将对应提交的完整源码 ZIP、锁文件、构建脚本与许可声明一并上传。不要把本地配置、签名文件或带私有服务配置的 APK 当成公共默认包。
- CI 继续执行验证和生成未签名包；新增更新功能不会自动发布 Release，也不会把本机签名密钥上传 CI。

本地已配置的音源仍按既有规则注入本地 APK。远端构建者提供自己的音源、服务与签名；应用更新不把私有音源配置上传到 GitHub。若分发包含私有配置的安装包，应使用受控的分发渠道，公共 GitHub 更新地址不适合承载秘密。

## Fork

构建时使用 `-PkinaraUpdateRepository=owner/repo` 改为自己的 GitHub Releases。仓库名只允许标准 owner/repo 字符；APK 包名和签名仍必须与用户已安装版本相同。版本信息解析、下载边界、损坏/截断/超大响应、取消清理、签名与 FileProvider 范围都有回归测试。系统安装及设备策略需要真机验收。
